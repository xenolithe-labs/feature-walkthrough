# Adversarial review of walkthrough-design

**Who:** a separate fresh agent, given only the skill folder, the brief's "The skill" section and the syntax skill (for the decoupling test). It was told to attack along eight lines, including a paper exercise (it designed a database-deadlock walkthrough). It did not open the cited URLs, so it checked consistency between `SKILL.md` and `sources.md`, not the quotes themselves. Date: 2026-11-20.

**Result:** 3 critical, 11 major, 13 minor findings, plus checklist rewordings. Below, the findings in the order of the report, the decision and the change.

## Critical

| #   | Finding                                                                                                                                               | Decision | Change                                                                                                                                    |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| C1  | "Touch as few views as it can" contradicts "keep state visible": a focus view that stages only touched views would hide the state table.              | Accept   | Rule is now "touch every view whose state the call depends on, and no other", with "relied on" marked. Checklist 15 reworded.             |
| C2  | "Highlight exactly the one change" plus "one idea per call" splits atomic events (transfer, rollback) into calls that show states that never existed. | Accept   | "Highlight everything the call changes, and nothing else." "Do not split an atomic event"; split only when effects have different causes. |
| C3  | "A fresh agent who knows nothing of the subject" is impossible for an LLM, and it is the only test an agent can run.                                  | Accept   | Section 10.3 is a cold-read protocol: texts only, treat undefined terms as unknown, list gaps, report as the weaker test.                 |

## Checklist rewordings

Accepted: split compound items (purpose, colour, values), "five random claims" for fact-checking, "three sentences or fewer", an n/a marker for loops and branches, reader-test items moved to a separate "Before you ship" group with the cold-read fallback, and item 11 (one-verb test) now stated as such. Rejected: "could you drop half the call and leave a true story" as a replacement for the one-verb test, because it is less answerable.

## Reviewer's paper exercise (deadlock)

Gaps it found and what addressed them: no success case (M10), opening call (M11), merge versus one-arrow-per-call (section 4 now says each message is its own call), blocked statements (M7), atomic rollback (C2), focus staging hiding the lock table (C1), two views asking similar questions (the "name the question" rule is now an artifact), engine choice (section 8: pick one and name its version), cut rule (section 2: "or a fact a kept call refers to"), long commands in names (section 5), design record location (M2).

## Not addressed

- Whether the two-view-pair default misleads for subjects with many co-equal actors was not tested beyond the reviewer's deadlock case.
- Length. The reviewer asked for a one-fifth cut from about 3,300 words. The revision is about 4,000 words including three worked examples and a 30-item checklist, so it grew: it added the procedure, the cold-read protocol and a non-message example, and fixed contradictions. The "why use a walkthrough" section became a paragraph and the contrast sentence was dropped, but this is not the cut asked for. A second review should judge whether it is read and what to cut.

## Field trials

The skill is being tried on the bundled demos, one at a time: an agent redoes a demo by following the skill, logs where it helped, where it disagreed, what was unclear and what the skill was silent on, and the skill is revised before the next demo.

### Trial 1: spreadsheet recalculation

Verdict from the trial: mixed. Better on substance (the reader can now say what goes wrong in the wrong order, that a formula cell can be skipped, and which cells were recomputed), worse on length (card text 2.2 times longer).

| Finding                                                                                                                                  | Decision | Change                                                                                                                              |
| ---------------------------------------------------------------------------------------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| "Pair what happens with what it changes" pushed toward a third view that made the result worse; the subject has no messages or code      | Accepted | The rule now applies when the subject has both; two views of state are enough otherwise; a third view must fit beside the other two |
| "Do not show the whole system at the start" is wrong when the starting state already exists, and conflicts with keeping the layout still | Accepted | Show existing state from the first call and mark only the part discussed; build up only what the run creates                        |
| The sentence-count limit let text double while every call passed                                                                         | Accepted | About 40 words in up to three sentences; joined statements count; an order of what to keep when not everything fits                 |
| "Label every relation" is too absolute when all arrows mean one thing                                                                    | Accepted | Say it once and leave the arrows bare                                                                                               |
| "About five things at once, group them" cannot apply when the things are the subject                                                     | Accepted | Exempted, with "keep the instance small"                                                                                            |
| Three rules named three places to define a term                                                                                          | Accepted | One rule in section 1; the others point to it                                                                                       |
| "Concurrency" heading hid guidance that applies to any unfixed order                                                                     | Accepted | Heading renamed                                                                                                                     |
| Silent on example size, a closing call, a call that changes nothing, and why the mechanism matters                                       | Accepted | Added "size the example", "Closing", and "a call that changes nothing"                                                              |
| Silent on what to do when the tool cannot show something                                                                                 | Accepted | One rule in the procedure: put it in the text or drop it, and record the gap                                                        |
| Cold read: unclear what the intro is and whether the reader sees the test question                                                       | Accepted | Stated; added "list every sentence read twice"; two rounds, storyboard then built                                                   |
| Checklist 16 fails a step name that the step itself defines                                                                              | Accepted | Reworded                                                                                                                            |
| Checklist 15 cannot fail when two views share ids                                                                                        | Kept     | It can fail in other designs; revisit after more trials                                                                             |
| Remove worked example A and the evidence tags in running text                                                                            | Deferred | One trial on a subject they do not fit is not enough; revisit after trials on message-based subjects                                |

Most valuable parts, by the trial's account: writing the test question's answer before designing, picking values that tell things apart, checking facts against a primary source (it showed the original demo's "sort" stage is not what the cited documentation describes), and the cold read.

### Trial 2: one React state update

Verdict from the trial: mixed. Better on substance and layout (batching is now shown, a separate "compare" phase that the cited documentation does not describe is gone, everything fits one screen, every claim has a pointer, and a browser test proves the displayed code behaves as described); worse on card length per call (mean 37 words against 21) and the picture of the component tree is gone.

| Finding                                                                                                         | Decision | Change                                                                                                                                           |
| --------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| The 40-word limit worked as a target: every card filled to it                                                   | Accepted | Reworded: as few words as state the change, many calls under 20; 40 is a ceiling; cards near the ceiling are a sign of a design problem          |
| The limit pushed out the prediction prompt the skill recommends                                                 | Accepted | A prediction question does not count toward the limit                                                                                            |
| The third-view rule is too narrow for a subject with two kinds of state, and "fits on screen" did not say where | Accepted | A second kind of state is a valid reason; the test is the default layout on an ordinary laptop; try folding it into the state view as rows first |
| The cold read's "treat as unknown" over-reports terms the reader is recorded as knowing                         | Accepted | The reader's known terms are handed over as a list; step names are included; act on unstated changes and re-read sentences first                 |
| Closing: a separate call, or the last event?                                                                    | Accepted | It is the last real event's call                                                                                                                 |
| A step's purpose sentence and the intro may not be shown by the tool                                            | Accepted | Check that the tool shows them before relying on them; otherwise put them in calls                                                               |
| "Read the cards aloud" was never possible                                                                       | Accepted | Removed                                                                                                                                          |
| Checklist items that only re-ask the record                                                                     | Partly   | Items 1 to 3 tightened and tied to the final state; the rest kept until more trials show which never fail                                        |
| Remove worked example B and the evidence caveats in bullets                                                     | Deferred | Trial 3 is a loop subject, which is what example B covers                                                                                        |

Rules revised after trial 1, as judged by trial 2: pairing events with state, and showing existing state from the start, both worked on a subject with code. The word limit stopped trial 1's doubling but became a target. One place to define a term was clear. The cold-read protocol worked as written; "sentences read twice" was its most productive list.

Both trials found that a step the original demo showed is not in the documentation it cites (a "sort" stage, a "compare" phase). Checking facts against the primary source is the rule that has paid most.

### Trial 3: binary search (found, and not found)

Verdict from the trial: mixed, in the same direction as the first two. Better on substance (the text now states every index and value, half the calls, no empty cards, the absent case ends on the general case and compares directly with the found one, and two views fit without a third pane); worse on words per card (mean 26 against 14) and seven of the absent run's twelve calls repeat the found run.

| Finding                                                                                                      | Decision | Change                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------ | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "Two paths equally long and important: make two walkthroughs" produced duplication and gave no test          | Accepted | Choose the alternative's data to share the opening; put it in a later step that starts where the paths part; a second walkthrough only when they share little                                                                                      |
| For code, "a call is one idea" did not say whether a passing guard is its own call                           | Accepted | New rule: a call is one idea, not one line; a passing guard joins the statement it guards; lay out the source so a call's lines are adjacent                                                                                                       |
| "For a protocol or algorithm that is a success case" contradicts a question about absence                    | Accepted | The run is the one that carries the test question                                                                                                                                                                                                  |
| A step's recap in its own text gives away the ending, now that step text is shown from the step's first call | Accepted | The recap belongs in the step's last call                                                                                                                                                                                                          |
| "Old and new" is noise for a value that is recomputed                                                        | Accepted | Give the old value when it meant something                                                                                                                                                                                                         |
| "Many calls need under 20 words" did not happen once each card carried values and a reason                   | Partly   | Reworded to "a simple call needs under 20", and a warning added that the cold read pushes text longer: check whether a view already shows the change first                                                                                         |
| The cold reader still listed things the views carry                                                          | Accepted | It is given the step texts and one line on what the views show before the first call; the order of its lists puts unstated changes and re-read sentences first                                                                                     |
| The skill is too long; tags, caveats, examples A and B and several checklist items never earned their place  | Accepted | Rewritten at about 3,800 words, from about 4,750: evidence tags and caveats moved out (they are in sources.md), the load and accessibility section folded into the others, three examples cut to two short ones, checklist cut from 30 items to 23 |
| The skill's own binary search example never ran the else branch, breaking its "size the example" rule        | Accepted | The example now uses the trial's data and both branches                                                                                                                                                                                            |

Across three trials, by each trial's own account, the parts that paid most were: writing the test question's answer before designing; sizing the example to that answer; choosing values that tell things apart; checking facts against a primary source; and the cold read. The checklist paid least for the time it took.

A pattern in all three: the redone walkthrough was better on substance and longer per card. The rules that add words (state old and new values, stand alone, state every change) are each reasonable; together, and reinforced by a cold reader who cannot see the views, they push text up. Revision 3 addresses that with the ceiling wording, the "simple call under 20" target, and the warning in the test section. Whether that is enough is for the next trial to show.
